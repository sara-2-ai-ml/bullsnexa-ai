How it works

From a rough brief to a decision in three steps.

You stay in control at every step: the agent drafts, the rules judge, and a person signs off on risk.

1

Describe

Write the brief in plain words or fill in the form. The agent pulls out the fields and you review them before anything runs.

2

Check

The agent looks up the policies and calls the rule checks. Missing details become questions, never guesses.

3

Decide

You get a verdict, a 0 to 100 score with reasons, a launch plan, and a clear record of every step.

The principle

The AI proposes. The rules decide.

A language model is good at reading messy text and choosing the next step. It is not trusted with the verdict.

AI agent

Suggests a step

Reads the brief and proposes which check to run next.

Backend

Validates it

Only known, authorized tools run, with timeouts and limits.

Rules engine

Scores the brief

Fixed, versioned rules produce the status and the score.

A person

Approves risk

Risky cases wait for a named reviewer, tied to the exact plan.

The model cannot change the budget, the dates, or the verdict.
Outcomes

Three clear answers, each with a reason.

READY

Go ahead and plan the launch

All required details are valid and no rule asks for a person to step in first.

Handoff: cleared
NEEDS REVIEW

Usable, but a person must sign off

For example, a budget above the review threshold, or EU lead generation that needs a privacy check.

Handoff: pending approval
BLOCKED

Fix the brief first

For example, a negative budget or an end date before the start date. No launch plan is built.

Handoff: not eligible

Illustrative audiences. BullsNexa is a prototype with no customers, names no clients and is not in production today.

Guardrails

Built to be checked, not just trusted.

Bounded execution

Limits on steps and tool calls, timeouts on every operation, and one narrow retry for transient errors.

Untrusted text stays data

Briefs, notes, and policy text can never act as instructions. Prompt injection is part of the test suite.

Approval tied to the plan

An approval is bound to a hash of the exact plan reviewed. Change the plan and the approval stops counting.

Every run is recorded

Brief, decision, each step with its timing, and the approval, all kept in the run history.

Works offline, honestly

Without an API key it runs on a labeled simulated provider. It is never presented as a real model.

Evaluated

Fifteen evaluation cases and a full offline test suite, including fault injection and tampering checks.
